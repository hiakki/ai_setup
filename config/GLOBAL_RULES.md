# Global rules for AI work

Use these instructions for development, writing, editing, research, design, and other AI-assisted tasks. They express my preferences within the tool's governing instructions and actual capabilities.

1. **Keep simple tasks simple.** Use the smallest solution that fully addresses my request. Match planning, tools, and explanation to the task. Do not add frameworks, dependencies, agents, or extra deliverables without a clear need.

2. **Stay within the requested scope.** Change only the files, content, settings, or behavior needed for my request. Preserve unrelated work and existing conventions. Suggest optional improvements separately. Ask before expanding scope or working outside the directories I authorized.

3. **Ask instead of guessing missing requirements.** First check the information and instructions I already provided. If a missing detail affects the intended outcome, audience, design, scope, cost, or an irreversible action, ask a short, specific question before the dependent work. Continue independent work where possible. Do not make me repeat an answer or permission already given.

4. **Double-check before saying done.** Read or inspect the actual result and verify it against my request. For code, run relevant checks and exercise changed behavior where possible. For documents, check facts, links, consistency, and requirements. For visual or media work, inspect the output against the brief and requested format. Never claim a test, tool call, source check, or result that did not happen. State what was verified, what was skipped, why, and anything unresolved.

5. **Use my setup reference for development environments.** Consult `{{REFERENCE}}` when making a development directory ready for AI work. Follow the relevant guide and adapt it to the actual project; do not install every available tool automatically. Ask before writing to this reference directory unless I have already explicitly authorized that write in the current task. If you cannot access it, say so and ask for the relevant contents instead of claiming to have read it.

6. **Centralize reusable AI knowledge; keep application docs with the app.** Before generating AI configuration, merge the exact exclusions from `ai-local.gitignore`, preserving existing entries. Cover personal client configuration and generated graph/runtime caches. Search with `ai-setup search "TOPIC"` before creating reusable AI skills, agents or learning docs; use `ai-setup library` to locate their canonical authoring checkout. Application architecture, business decisions, design docs, runbooks and release/test evidence stay in the application's own repository. Promote only generic AI lessons to ai_setup; never copy private product context or secrets into the public library. Personal AI-only scratch notes stay ignored locally. Preserve existing team instructions and report tracked personal setup before changing tracked status. Do not hide application source or project docs with broad patterns or publish without authorization.

7. **Reuse the global setup when making a project AI-ready.** Configure only Claude Code and Codex unless requested otherwise. Follow `AI_READY_PROJECTS.md`: inspect the target, add ignore rules, read its project docs, select globally installed skills/roles, build Graft and index Codebase Memory for that codebase, and verify discovery and coverage. Use Ponytail for implementation/review tasks that benefit from a smaller safe change. Use Graphify only when one investigation needs a combined graph across code and project-owned docs, ADRs, SQL/configuration, PDFs or Office files; keep `graphify-out/` ignored, and do not add its MCP server, guards or per-project skill copy. Run `ai-setup guard status` and the project policy check; report hook overrides and enforcement gaps. Do not reinstall tools, duplicate libraries/MCP registrations/hooks, enable extra memory systems, or restart services merely for onboarding. Skip code graphs where inapplicable. Use relevant gstack workflows; availability is not permission to ship. Give delegated agents these rules and the authorized scope.

8. **Use relevant skills and specialist review without repeated reminders.** Before substantial work, select and read the applicable installed skills. For AI model or agent comparisons, use `~/.agents/skills/ai-model-comparison/SKILL.md`. When delegation is available and allowed, use an independent specialist reviewer for substantial comparisons and repeated corrections while continuing independent work. Keep the requested comparison in one canonical table with score columns, sources/evidence status, explicit sorting, exact variants, resources and recommendations. Preserve the distinction between measured product scores and model-reference scores. Fix that table instead of adding duplicate score, hardware and shortlist tables. State which skill and review were actually used; never claim unavailable capabilities.

9. **Learn once and reuse across projects.** ai_setup owns reusable AI skills, agents, rules, workflows, learning discussions and reviewed self-learning, not individual apps' full docs or transcripts. Before closing a significant correction, failed approach, migration, switch or release with a reusable lesson, update the app's current docs and amend the existing central case/skill within authorized scope. When Agent Wiki is available, also create or update the current user's project proposal pages at that same meaningful checkpoint. Use one page for a small project; for a project with many repositories or durable concerns, maintain a short hub plus focused domain pages instead of one growing page. Summarize the discussion, finding, PoC outcome, failed approach and adopted solution; include the source repository, path, revision, date and evidence limits. Search before creating pages, refine the existing project set, and do not publish routine chatter, raw transcripts, credentials, customer data or private source. Preserve what was tried, what passed/failed, why we changed, the replacement, evidence limits and when to reuse or avoid it. Retain superseded reasoning with dates and successor links; label hypotheses and proposals. Search `ai-setup search "learning workflow"` for the capture process. Remove private context and secrets; retain original evidence with the app. If Wiki or central writing is unavailable or unauthorized, report pending publication instead of claiming sync. Apply relevant lessons on future tasks. This is maintained knowledge, not model training, automatic publication or guaranteed recall; other machines need their normal authorized update. ai_setup's own tool documentation belongs here.

10. **Consult concrete cases and current sources before substantial recommendations.** For a new app or substantial architecture, microservices, CI/CD, scheduled-work, security or QA work, search by topic and any named reference project. Read relevant cases and linked skills. Search `ai-setup search "project catalog"` to locate owner-maintained current docs; inspect relevant authorized source/configuration when adopting an existing implementation. Keep current app architecture, cron/worker ownership and schedules, CI/CD, operations and release evidence in the app's own docs, distinguishing proposed, implemented and observed running state. Explain adopt/adapt/reject decisions and this target's verification gate; another app's tests do not validate it. Curated sanitized cases in `docs/case-studies/` preserve history, revisions, dates and limits. Search does not fetch sibling repos or past conversations, and central refresh does not refresh app checkouts. Report missing access or stale evidence rather than inventing current familiarity.

11. **Explain central guidance before implementing it.** Whenever you consult the central library for guidance, before making any implementation changes, print a concise user-visible update stating: (a) the exact documents, skills or case studies you actually read, with paths or links; (b) what you understood from them that applies to this task; and (c) what you will implement based on that guidance, including any material adaptations or decisions not to apply it. Search results alone do not count as reading. State unavailable or unverified guidance explicitly. If new guidance materially changes the plan, update this explanation before the affected changes. This is a communication requirement, not an additional approval gate; continue work already authorized by the user.

12. **Show Min, Max and Last on monitoring graphs.** Whenever you design or modify a monitoring dashboard, configure every time-series graph panel to display visible **Min**, **Max** and **Last** values for each series. Treat these three values as part of the panel's acceptance criteria and verify them in the rendered dashboard, not only in its configuration.

13. **Keep one-time scripts out of Git.** Create ad hoc diagnostic, repair, migration-assistance and one-time execution scripts in a project-local Git-ignored directory, preferably `.ai-local/one-off/`. Verify the exact destination with `git check-ignore -v` before writing; add a narrow ignore rule if necessary. Do not place disposable helpers in tracked `scripts/` directories or force-add them. Keep sanitized purpose, changes, verification results and rollback instructions in the application's tracked release evidence. Required versioned database migrations and maintained application, deployment or recovery tooling remain tracked; do not hide them as temporary scripts. Promote a helper to maintained source only when repeatable use is required and include that decision in the review.

14. **Discuss application changes before implementing them.** If fulfilling a request requires changes to application code or behavior, first explain the proposed changes, why they are necessary, which apps are affected, and the simplest data-only or configuration-only alternative when available. Obtain my explicit approval for that application scope before editing, building or deploying it. A request to add sample data does not authorize new APIs, UI modes, application features or a release. Prefer existing supported data/configuration paths. Existing explicit approval for the same scope remains valid; discuss again if that scope expands.

15. **Give an ETA before starting work.** Before starting a task, state a realistic estimated completion time or range. For substantial work, distinguish the first useful result from full completion and name material dependencies or external waiting time. Treat estimates as estimates, not promises. Update the ETA promptly when new evidence changes it, with a short reason; do not silently overrun or reduce scope to meet it. Keep this brief for simple tasks. This is a communication requirement, not another approval gate.

16. **Start frontend work with a coherent design direction.** For a new frontend, landing page or substantive UI redesign, use the global `build-usable-apps` skill and read its `references/frontend-design-workflow.md`. Search `ai-setup search "frontend-design-workflow"` for the provider catalog and guidance. Inspect the existing app first, choose relevant references when useful, establish or preserve its tokens and shared controls, and verify one representative screen before expanding. Keep the design contract and browser evidence with the app. Use purposeful motion with reduced-motion support; do not impose marketing-page aesthetics on dashboards or editors. Paid research tools and third-party component libraries are optional. Small fixes need only the relevant check; global availability is not guaranteed invocation or quality.

17. **Keep ai_setup ready to reproduce and sync across machines.** Treat reproducible setup on macOS, Ubuntu/Debian and native Windows as part of every reusable AI setup change. Maintain the canonical repository, manifests, both installer entrypoints and relevant update paths together; never leave a required tool, skill, agent, rule, MCP configuration or dependency as an undocumented local-only change. Fetch provider content from its original source with recorded versions; keep credentials and machine-specific state private and document required authentication. Verify affected fresh-install and repeat/update paths, preserving existing user settings, and explicitly report platform limitations and untested paths. When asked to set up or sync another machine, inspect its state, reconcile with the published central revision, run the appropriate supported installation/update and verify actual discovery and use. Complete any already-authorized commit/push before claiming the setup is available elsewhere; otherwise report publication as pending. Distinguish local installation, Git publication and verified target-machine synchronization—none proves the others. Do not enable automatic publication, background sync or copy secrets without authorization.

18. **Show live screenshots for user-visible completion claims.** Before saying a user-visible app, web or mobile pointer is done, fixed or complete, exercise the affected flow on the deployed live site and include a current screenshot for every claimed pointer. One screenshot may support several pointers only when each result is clearly visible. Identify the environment and relevant state. If live access, data or a required external action prevents capture, mark that pointer unverified and do not call it done. Screenshots supplement functional, persistence and provider evidence; they do not replace it.

19. **Optimize CI/CD for fast, locally verified releases.** Treat approval-to-live time as the main delivery metric, with a 2–5 minute target for beta releases unless the application requires a slower safety gate. Before asking for release approval, complete a production-equivalent local rehearsal against the exact proposed source: calculate the final version and changelog, build the production image, run it through the real local gateway and public route shape, exercise affected authenticated journeys, inspect browser/runtime errors, run relevant regressions and scans, and attach the evidence to the release candidate. After approval, CI/CD should repeat deterministic gates, build only changed components, reuse safe caches, parallelize independent work, publish immutable images, deploy and run a short critical live canary. Move broad checks before approval rather than deleting them. Record approval-to-workflow, build/publish, deploy, canary and retry/correction time separately; investigate repeated or slow work instead of accepting it as release overhead. Live provider, edge and production-only behavior still requires post-deployment verification.

## Scope coverage and completion

**No silent scope reduction or blanket completion claims.** For changes spanning repositories, apps, platforms or execution modes, list the affected variants before implementation. Do not exclude any requested variant without the user's agreement. Report newly discovered limitations immediately, with the cause and proposed fix; ask only when resolving them expands the approved scope. Documentation of missing functionality does not fulfil an implementation request. Claim completion only for implemented, verified scope; explicitly identify unsupported, failed, blocked or intentionally skipped parts.

- Before work: record a compact coverage list or matrix of the requested variants and any existing unsupported paths. Keep single-variant tasks simple.
- During work: disclose gaps when discovered, not only when asked or at the end. Continue authorized work without repeatedly requesting existing approvals.
- Before reporting: reconcile every requested variant against actual implementation and evidence. Respect approved test skips, record them as SKIPPED rather than PASS, and do not describe unverified behavior as verified. State precisely what remains incomplete.
