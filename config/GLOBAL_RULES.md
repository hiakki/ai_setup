# Global rules for AI work

Use these instructions for development, writing, editing, research, design, and other AI-assisted tasks. They express my preferences within the tool's governing instructions and actual capabilities.

1. **Keep simple tasks simple.** Use the smallest solution that fully addresses my request. Match planning, tools, and explanation to the task. Do not add frameworks, dependencies, agents, or extra deliverables without a clear need.

2. **Stay within the requested scope.** Change only the files, content, settings, or behavior needed for my request. Preserve unrelated work and existing conventions. Suggest optional improvements separately. Ask before expanding scope or working outside the directories I authorized.

3. **Ask instead of guessing missing requirements.** First check the information and instructions I already provided. If a missing detail affects the intended outcome, audience, design, scope, cost, or an irreversible action, ask a short, specific question before the dependent work. Continue independent work where possible. Do not make me repeat an answer or permission already given.

4. **Double-check before saying done.** Read or inspect the actual result and verify it against my request. For code, run relevant checks and exercise changed behavior where possible. For documents, check facts, links, consistency, and requirements. For visual or media work, inspect the output against the brief and requested format. Never claim a test, tool call, source check, or result that did not happen. State what was verified, what was skipped, why, and anything unresolved.

5. **Use my setup reference for development environments.** Consult `{{REFERENCE}}` when making a development directory ready for AI work. Follow the relevant guide and adapt it to the actual project; do not install every available tool automatically. Ask before writing to this reference directory unless I have already explicitly authorized that write in the current task. If you cannot access it, say so and ask for the relevant contents instead of claiming to have read it.

6. **Centralize reusable AI knowledge; keep application docs with the app.** Before generating AI configuration, merge the exact exclusions from `ai-local.gitignore`, preserving existing entries. Cover personal client configuration and generated graph/runtime caches. Search with `ai-setup search "TOPIC"` before creating reusable AI skills, agents or learning docs; use `ai-setup library` to locate their canonical authoring checkout. Application architecture, business decisions, design docs, runbooks and release/test evidence stay in the application's own repository. Promote only generic AI lessons to ai_setup; never copy private product context or secrets into the public library. Personal AI-only scratch notes stay ignored locally. Preserve existing team instructions and report tracked personal setup before changing tracked status. Do not hide application source or project docs with broad patterns or publish without authorization.

7. **Reuse the global setup when making a project AI-ready.** Configure only Claude Code and Codex unless requested otherwise. Follow `AI_READY_PROJECTS.md`: inspect the target, add ignore rules, read its project docs, select globally installed skills/roles, build Graft and index Codebase Memory for that codebase, and verify discovery and coverage. Run `ai-setup guard status` and the project policy check; report hook overrides and enforcement gaps. Do not reinstall tools, duplicate libraries/MCP registrations/hooks, enable extra memory systems, or restart services merely for onboarding. Skip code graphs where inapplicable. Use relevant gstack workflows; availability is not permission to ship. Give delegated agents these rules and the authorized scope.

8. **Use relevant skills and specialist review without repeated reminders.** Before substantial work, select and read the applicable installed skills. For AI model or agent comparisons, use `~/.agents/skills/ai-model-comparison/SKILL.md`. When delegation is available and allowed, use an independent specialist reviewer for substantial comparisons and repeated corrections while continuing independent work. Keep the requested comparison in one canonical table with score columns, sources/evidence status, explicit sorting, exact variants, resources and recommendations. Preserve the distinction between measured product scores and model-reference scores. Fix that table instead of adding duplicate score, hardware and shortlist tables. State which skill and review were actually used; never claim unavailable capabilities.

9. **Learn once and reuse across projects.** ai_setup owns reusable AI skills, agents, rules, workflows, learning discussions and reviewed self-learning, not individual apps' full docs or transcripts. Before closing a significant correction, failed approach, migration, switch or release with a reusable lesson, update the app's current docs and amend the existing central case/skill within authorized scope. Preserve what was tried, what passed/failed, why we changed, the replacement, evidence limits and when to reuse or avoid it. Retain superseded reasoning with dates and successor links; label hypotheses and proposals. Search `ai-setup search "learning workflow"` for the capture process. Remove private context and secrets; retain original evidence with the app. If central writing is unavailable or unauthorized, report pending promotion instead of claiming sync. Apply relevant lessons on future tasks. This is maintained knowledge, not model training, automatic publication or guaranteed recall; other machines need their normal authorized update. ai_setup's own tool documentation belongs here.

10. **Consult concrete cases and current sources before substantial recommendations.** For a new app or substantial architecture, microservices, CI/CD, scheduled-work, security or QA work, search by topic and any named reference project. Read relevant cases and linked skills. Search `ai-setup search "project catalog"` to locate owner-maintained current docs; inspect relevant authorized source/configuration when adopting an existing implementation. Keep current app architecture, cron/worker ownership and schedules, CI/CD, operations and release evidence in the app's own docs, distinguishing proposed, implemented and observed running state. Explain adopt/adapt/reject decisions and this target's verification gate; another app's tests do not validate it. Curated sanitized cases in `docs/case-studies/` preserve history, revisions, dates and limits. Search does not fetch sibling repos or past conversations, and central refresh does not refresh app checkouts. Report missing access or stale evidence rather than inventing current familiarity.

11. **Show live screenshots for user-visible completion claims.** Before saying a user-visible app, web or mobile pointer is done, fixed or complete, exercise the affected flow on the deployed live site and include a current screenshot for every claimed pointer. One screenshot may support several pointers only when each result is clearly visible. Identify the environment and relevant state. If live access, data or a required external action prevents capture, mark that pointer unverified and do not call it done. Screenshots supplement functional, persistence and provider evidence; they do not replace it.

These are portable personal preferences loaded through each client's supported instruction mechanism. See the project-onboarding guide at `{{REFERENCE}}/AI_READY_PROJECTS.md`.
